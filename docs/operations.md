# Операції

Довідник з експлуатації розгорнутого SlangUA: перше розгортання, оновлення й
відкат, бекапи і відновлення, стеля на логи, зовнішній моніторинг і ті
налаштування зворотного проксі, які відрізняються від типових не випадково.
Перелік змінних — у [configuration.md](configuration.md), порядок робіт стадії
розгортання — у [`plans/ROADMAP.md`](../plans/ROADMAP.md#stage-9--deployment-in-progress).

## Перше розгортання

Послідовність нижче написана так, щоб її можна було виконати за один сеанс, не
здогадуючись. Скрипти, які автоматизують копіювання на конкретний сервер, живуть
**поза репозиторієм** (вони містять адресу й обліковий запис — див.
[10-repository-hygiene.md](../plans/docs/10-repository-hygiene.md)); сама
процедура — тут.

### 0. Що має бути на машині

Docker з плагіном `compose`, **хостовий** nginx (термінатор TLS — той, що в
образі `frontend`, роздає лише статику й TLS не бачить), `certbot`, і домен, у
якого `A`-запис уже вказує на цей сервер. Останнє — перше, що варто перевірити:
`certbot` у режимі `--webroot` без робочого DNS не видасть сертифікат, і це
з'ясується вже після половини роботи.

`node` на хості не потрібен — усе, що потребує Node, виконується в контейнерах.
Єдиний виняток описаний у кроці 2.

### 1. Дерево на сервері

```sh
sudo mkdir -p /opt/slangua && sudo chown "$USER" /opt/slangua
# далі — розпакувати архів релізу або `git clone` у /opt/slangua
cd /opt/slangua
```

Каталог із дампами краще тримати **поза** цим деревом: `docker compose down -v`
всередині робочої копії — це саме та команда, після якої дамп у ній лишається
єдиною копією, і лежить він на тому ж диску, що й база.

```sh
sudo mkdir -p /var/backups/slangua && sudo chmod 700 /var/backups/slangua
```

`0700` **до** першого запуску: інакше каталог створить Compose і зробить це з
`0755`, а виправляти права після появи дампів доведеться руками.

### 2. `.env` на сервері

```sh
cp .env.example .env && chmod 600 .env
openssl rand -hex 32     # JWT_SECRET
openssl rand -hex 32     # REFRESH_TOKEN_HMAC_SECRET
openssl rand -base64 32  # PREVIEW_ROOT_KEY
openssl rand -hex 32     # POSTGRES_PASSWORD
```

Заповнити треба: чотири секрети вище, `TELEGRAM_BOT_TOKEN` з BotFather,
`CORS_ALLOWED_ORIGINS=https://<домен>`, `BACKUP_DIR=/var/backups/slangua` і
хоча б один `*_API_KEY` AI-провайдера. `NODE_ENV`, `HOST`, `PORT`,
`TRUST_PROXY`, `DATABASE_URL` і `REDIS_URL` **не чіпайте**: для контейнера `api`
їх задає сам
[`docker-compose.production.yml`](../docker-compose.production.yml) через
`environment:`, і це перекриває значення з `env_file`. Правка `TRUST_PROXY` у
`.env` не дасть нічого — рівно та плутанина, на яку варто витратити один рядок
попередження.

Заглушки з `.env.example` не треба вичищати вручну: усі значення `example-only`
і демонстраційний `PREVIEW_ROOT_KEY` відхиляються при старті під
`NODE_ENV=production`, тому забутий рядок — це впав контейнер із названою
помилкою, а не тихо небезпечний деплой.

**Значення з `$` беріть в одинарні лапки** — у production цей файл читає парсер
Compose, який виконує інтерполяцію; подробиці й пастка з `ADMIN_PASSWORD_HASH` —
у [configuration.md](configuration.md).

Хеш пароля адмінки — єдине, що робиться **не на сервері**: `node
scripts/hash-admin-password.mjs` потребує Node, тому виконайте його на робочій
машині й перенесіть готовий рядок. Пароль скрипт читає зі stdin і у вивід не
кладе.

### 3. nginx: спочатку HTTP-шаблон

Порядок саме такий, бо HTTPS-шаблон містить `ssl_certificate` на файл, якого ще
не існує, — nginx із ним просто не запуститься.

```sh
sudo mkdir -p /var/www/certbot
sudo sh -c 'sed "s/__SERVER_NAME__/example.com/g" \
  /opt/slangua/deploy/nginx/slangua.http.conf.template \
  > /etc/nginx/conf.d/slangua.conf'
sudo nginx -t && sudo systemctl reload nginx
```

Підставляти домен треба **всюди** (`g`): у HTTPS-шаблоні `__SERVER_NAME__`
зустрічається і в `server_name`, і у шляхах до сертифікатів.

### 4. Сертифікат і його поновлення

```sh
sudo certbot certonly --webroot -w /var/www/certbot -d example.com
sudo sh -c 'sed "s/__SERVER_NAME__/example.com/g" \
  /opt/slangua/deploy/nginx/slangua.https.conf.template \
  > /etc/nginx/conf.d/slangua.conf'
sudo nginx -t && sudo systemctl reload nginx
```

Дві речі, на яких це ламається найчастіше:

- HTTPS-шаблон посилається на `/etc/letsencrypt/options-ssl-nginx.conf` і
  `ssl-dhparams.pem`. Ці файли створює **плагін** certbot для nginx, а не сам
  certbot: без пакета `python3-certbot-nginx` (у Debian/Ubuntu) їх не буде, і
  `nginx -t` впаде на неіснуючому `include`.
- Поновлення проходить тим самим `--webroot`, тому блок
  `location ^~ /.well-known/acme-challenge/` мусить лишатися доступним по
  **HTTP**. У HTTPS-шаблоні він тому й стоїть у 80-му `server` *перед* редиректом
  на HTTPS — не прибирайте його, «щоб було чисто».

Поновлення виконує таймер із пакета certbot; нового конфіга nginx він сам не
підхоплює, тому один хук:

```sh
sudo mkdir -p /etc/letsencrypt/renewal-hooks/deploy
sudo sh -c 'printf "#!/bin/sh\nsystemctl reload nginx\n" \
  > /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh'
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
sudo certbot renew --dry-run
```

Без хука сертифікат поновиться, а nginx роздаватиме старий, поки хтось не
перезавантажить його руками — тобто до першого «у мене сайт не відкривається»
через 90 днів.

### 5. Перший запуск

```sh
cd /opt/slangua
C="docker compose -f docker-compose.production.yml"
$C up -d --build
$C ps
curl -fsS http://127.0.0.1:3000/health/ready && echo   # зсередини
curl -fsS https://example.com/health/ready && echo     # через хостовий nginx
```

Міграції застосовує сама команда сервісу `api` (`npx prisma migrate deploy`),
окремого кроку немає. Перший старт довший за наступні: `start_period: 60s` у
healthcheck саме для цього.

Друга команда `curl` — це водночас перевірка, що блок `location = /health/ready`
на місці. Якщо у відповідь прийшов HTML замість JSON, шаблон підставлений
неправильно і зовнішній монітор буде вічно зеленим — див.
[Зовнішній моніторинг](#зовнішній-моніторинг).

### 6. Перший адмін і Mini App

Допишіть у `.env` свій числовий Telegram-id у `ADMIN_TELEGRAM_IDS` і хеш із
кроку 2 в `ADMIN_PASSWORD_HASH`, потім `$C up -d api`. Поки список порожній,
усі маршрути `/api/v1/admin/*` віддають `404` — той самий, що й неіснуючий шлях,
тому «адмінка не працює» і «адмінки немає» виглядають однаково. Правила доступу —
у [`plans/docs/06-security.md`](../plans/docs/06-security.md#admin-access).

Останнє — зареєструвати `https://example.com` як URL Mini App у BotFather
(`/newapp` або кнопка меню бота) і відкрити застосунок у Telegram.

## Оновлення і відкат

### Оновлення

```sh
cd /opt/slangua
C="docker compose -f docker-compose.production.yml"
# 0. Позачерговий дамп, якщо в релізі є міграція. Див. чому — нижче.
$C run --rm --entrypoint sh db-backup /usr/local/bin/backup-postgres.sh --once
# 1. Нове дерево на місці (архів/git pull), далі:
$C up -d --build
$C ps && $C logs --tail=30 api
```

`up -d` перестворює лише ті контейнери, чия конфігурація або образ змінилися.
Два випадки, коли цього **не** досить і потрібен `--force-recreate`: змінився
`scripts/backup-postgres.sh` (монтування одного файла тримається за inode) і
змінилися опції `logging:` (вони фіксуються при створенні контейнера). Обидва
описані нижче у своїх розділах.

### Відкат

Відкат образу і відкат схеми — це дві різні операції, і плутати їх дорого.

**Якщо в релізі не було міграції** — поверніть попереднє дерево (`git checkout
<тег>`) і `up -d --build`. Це все.

**Якщо міграція була** — `prisma migrate deploy` не має кроку «вниз». Схема вже
змінена, і старий образ побачить базу, якої не очікує: у кращому разі це зайва
колонка, яку він ігнорує, у гіршому — перейменована або видалена, і застосунок
падає на кожному запиті. Тому єдиний надійний відкат тут — **відновлення з
дампа, знятого перед оновленням** (крок 0 вище), і саме тому цей крок стоїть
першим. Процедура — у [Відновлення з дампа](#відновлення-з-дампа).

## Бекапи Postgres

### Як це працює

Бекапи робить сервіс `db-backup` із
[`docker-compose.production.yml`](../docker-compose.production.yml) — окремий
контейнер на **тому самому образі**, що й база (`postgres:16-alpine`). Це не
дрібниця: `pg_dump` старішої версії відмовляється дампити новіший сервер, тому
при оновленні Postgres обидва теги треба піднімати разом.

Сам розклад — у [`scripts/backup-postgres.sh`](../scripts/backup-postgres.sh),
який змонтований у контейнер лише для читання. Перезбирати образ після правки
скрипта не потрібно, але й `restart` тут не працює:

```sh
docker compose -f docker-compose.production.yml up -d --force-recreate db-backup
```

Монтування **одного файла** прив'язане до inode. Будь-який редактор (і деплой,
який копіює дерево заново) створює новий файл, а контейнер, що вже працює,
продовжує виконувати старий, видалений. `restart` перевикористовує той самий
контейнер разом зі старим монтуванням — тому саме `--force-recreate`.

Що робить скрипт:

- один `pg_dump` на добу о `BACKUP_AT` (UTC), плюс один одразу після старту,
  **якщо** за останні 24 години дампа ще не було. Тому рестарт не пропускає
  добу — і водночас контейнер у циклі падінь не прокручує історію заново;
- пише в тимчасовий файл і переносить його в `daily/` лише коли дамп повністю
  готовий. Недороблений дамп ніколи не потрапляє в каталог і ніколи не
  зараховується як копія;
- `pg_dump` і `gzip` — два окремі кроки, а не конвеєр: POSIX-оболонка не бачить
  код виходу лівої частини `|`, тож зламаний дамп у конвеєрі виглядав би
  успішним;
- у неділю (ISO-день 7) додатково створює **жорстке посилання** на той самий
  файл у `weekly/`. Тижнева копія не займає місця, поки живі обидва імені, а
  видалення одного не чіпає інший;
- тримає `BACKUP_KEEP_DAILY` найновіших файлів у `daily/` і
  `BACKUP_KEEP_WEEKLY` у `weekly/`, рахуючи лише `*.sql.gz` — сторонні файли в
  каталозі не зникають;
- падіння одного дампа не завершує розклад: у скрипті свідомо немає `set -e`.
  Помилка йде в `stderr` контейнера, наступна спроба буде за розкладом.

Формат — звичайний SQL, стиснений gzip: для відновлення потрібен лише `psql`.
Процедура, яку виконують під тиском, не повинна залежати ні від чого більшого.

Ім'я файлу — час дампа за UTC: `slangua-20260827T033000Z.sql.gz`.

### Перевірити, що бекапи справді робляться

Розклад — не доказ. Команди нижче припускають типовий `BACKUP_DIR=./backups` —
підставте свій шлях у `B`, бо оболонка хоста змінних із `.env` не бачить.

```sh
cd /opt/slangua                       # каталог з docker-compose.production.yml
C="docker compose -f docker-compose.production.yml"
B=./backups

# 1. Позачерговий дамп прямо зараз (те саме, що робити перед міграцією).
$C run --rm --entrypoint sh db-backup /usr/local/bin/backup-postgres.sh --once

# 2. Що лежить у каталозі і якого розміру.
sudo ls -lh "$B"/daily "$B"/weekly

# 3. Лог сервісу: рядок `wrote daily/...` на кожен дамп, `ERROR` на кожну невдачу.
$C logs --tail=50 db-backup
```

Дамп нульового або підозріло малого розміру — це не бекап. Цілісність архіву
перевіряється без розпакування:

```sh
sudo gzip -t "$B"/daily/slangua-<стамп>.sql.gz && echo ok
sudo zcat "$B"/daily/slangua-<стамп>.sql.gz | head -20
```

У другій команді має бути шапка `pg_dump` і `CREATE TABLE`, а не порожньо.

### Відновлення з дампа

Це руйнівна операція: вона знищує поточний вміст бази. Перед нею варто зробити
`--once` — навіть якщо база здається зламаною, її поточний стан ще може
знадобитися.

```sh
cd /opt/slangua                       # каталог з docker-compose.production.yml
C="docker compose -f docker-compose.production.yml"
B=./backups                           # ваш BACKUP_DIR

# 1. Прибрати тих, хто пише в базу. Frontend хай лишається — користувач побачить
#    помилку застосунку, а не порожню сторінку.
$C stop api db-backup

# 2. Чиста база. Дамп знятий із --no-owner --no-privileges, тому відновлюється
#    під того користувача, яким запущений psql.
$C exec -T db psql -U slangua -d postgres -c 'DROP DATABASE slangua;'
$C exec -T db psql -U slangua -d postgres -c 'CREATE DATABASE slangua OWNER slangua;'

# 3. Залити дамп. Файли належать root, тому gunzip іде через sudo, а psql --
#    через socket у контейнері, де пароль не потрібен.
sudo gunzip -c "$B"/daily/slangua-<стамп>.sql.gz \
  | $C exec -T db psql -U slangua -d slangua -v ON_ERROR_STOP=1

# 4. Підняти застосунок. `prisma migrate deploy` у команді сервісу застосує ті
#    міграції, яких у дампі ще не було, -- це штатний випадок, якщо образ новіший
#    за дамп.
$C start api db-backup

# 5. Переконатися, що піднялося і дані на місці.
curl -fsS http://127.0.0.1:3000/health/ready && echo
$C exec -T db psql -U slangua -d slangua \
  -c 'SELECT count(*) AS users FROM "User";' \
  -c 'SELECT count(*) AS translations FROM "Translation";'
```

`ON_ERROR_STOP=1` тут обов'язковий: без нього `psql` дійде до кінця файлу,
проковтнувши помилки, і залишить напівживу базу з нульовим кодом виходу.

Після відновлення всі активні сесії стають недійсними: `RefreshToken` — рядки в
базі, і ті, що були видані після зняття дампа, у ній відсутні. Користувачі
переавтентифікуються самі при наступному відкритті Mini App; окремих дій це не
потребує.

### Чого бекапи не покривають

- **Redis не дампиться, і це рішення, а не пропуск.** Там немає нічого, що не
  відтворюється саме: ліміти згасають за вікном, кеш preview зашифрований і
  короткоживучий, метрики адмінки згасають за термінами ключів. Єдине, що
  переживає рестарт, — кіл-світч провайдерів (`ai:provider:disabled`), і його
  дешевше поставити руками, ніж відновлювати з копії. `appendonly yes` у сервісі
  `redis` тримає дані між перезапусками контейнера; втрата томика Redis коштує
  скинутих лімітів, а не даних користувачів.
- **Шифрування дампів немає.** Дамп — це повний текст усіх перекладів і
  Telegram-id усіх користувачів. Тому контейнер працює від `root` і не
  поступається правами, а скрипт додатково ставить `umask 077`: каталоги
  `daily/` і `weekly/` виходять `0700`, файли — `0600`. Самого лише `root` як
  власника було б **недостатньо** — типовий `umask 022` дав би `0644`, тобто дамп
  читав би будь-який акаунт на хості. Якщо каталог існував до появи `umask`,
  права виправляються один раз: `sudo chmod -R go-rwx "$BACKUP_DIR"`. `BACKUP_DIR`
  також не має лежати там, куди дивиться вебсервер. Якщо дампи виїжджають із
  машини — шифруйте їх на тому боці.
- **Копія на тому ж диску — не бекап від втрати диска.** `BACKUP_DIR` захищає від
  помилкового `DELETE`, невдалої міграції і зіпсованого тому Postgres, але не від
  смерті машини. Вивезення копії на інший хост — окрема задача оператора
  (`rsync`/`scp` за розкладом на хості), у compose її свідомо немає: інакше
  репозиторій мусив би знати адресу й ключ чужого сервера.
- **`.env` у дамп не входить.** Без `PREVIEW_ROOT_KEY`, `JWT_SECRET` і
  `REFRESH_TOKEN_HMAC_SECRET` відновлена база працює, але всі сесії й preview-кеш
  недійсні. Копія `.env` зберігається окремо від репозиторію й окремо від дампів.

### Що перевірено, а що ні

Скрипт перевірений у Linux-пісочниці із заглушками замість `pg_dump`/`pg_isready`:
синтаксис (`sh -n`, `dash -n`), режим `--once`, жорстке посилання тижневої копії
(той самий inode), права після `umask 077` (каталоги `0700`, дампи `0600`),
утримання 7/4 із видаленням найстаріших і без дотику до
сторонніх файлів, невдача `pg_dump` (файл не лишається, код виходу 1),
пропуск дампа на старті, коли свіжий уже є, арифметика розкладу для «октальних»
годин (`08:30`, `09:09`) і зупинка на некоректних `BACKUP_AT`/`BACKUP_KEEP_*`.

**Справжнє відновлення на розгорнутому сервері ще не виконувалося.** Процедура
вище написана, але не відрепетирувана — це пункт
[9.9](../plans/ROADMAP.md#stage-9--deployment-in-progress) («відновлення, яке
виконали»). До того моменту бекапи слід вважати перевіреними лише як механіка
зняття копій.

## Логи: стеля і ротація

### Чому це пункт про доступність даних, а не про порядок

Драйвер `json-file`, який Docker використовує за замовчуванням, **не має власного
обмеження розміру**. pino пише рядок JSON на кожен запит у stdout, nginx образу
`frontend` — рядок на кожен ассет, Postgres — на кожну контрольну точку. Без
стелі єдине, що зупиняє це зростання, — заповнений диск, а цей стек не деградує
плавно: Postgres перестає приймати записи, `pg_dump` віддає обрізаний файл, і
копія, яка мала б урятувати ситуацію, стає тим, що ламається першим.

Тому в [`docker-compose.production.yml`](../docker-compose.production.yml) кожен
сервіс має `logging:`. `max-size` — коли поточний файл ротується, `max-file` —
скільки файлів зберігається разом із поточним, тобто добуток і є стеля на сервіс:

| Сервіс | `max-size` × `max-file` | Стеля |
| ------ | ----------------------- | ----- |
| `api` | `10m` × 5 | 50 МБ |
| `db` | `10m` × 3 | 30 МБ |
| `redis` | `10m` × 3 | 30 МБ |
| `frontend` | `10m` × 3 | 30 МБ |
| `db-backup` | `10m` × 3 | 30 МБ |
| | | **170 МБ разом** |

`api` отримує глибше вікно свідомо: stdout pino — єдине місце, де лишається
стектрейс і необрізане повідомлення. Фід помилок в адмінці — це вікно, а не
архів (`ADMIN_ERROR_FEED_MAX` записів із TTL на весь ключ), тож інцидент
відтворюють саме з цих 50 МБ.

Це ліміти, а не резервування: місце займає лише те, що справді записано.
Решта сервісів ділять один якір `x-logging`, щоб новий сервіс не можна було
додати «без логів» непомітно — забути `logging:` помітно одразу, бо всі інші
рядки однакові.

### Перевірити, що стеля справді діє

`logging:` застосовується **при створенні контейнера**. Правка в compose нічого
не змінює для вже запущеного — `docker compose up -d` перестворить контейнер сам,
бо конфігурація змінилася, а от `restart` збереже старі налаштування. Перевіряти
треба не файл, а контейнер:

```sh
cd /opt/slangua                       # каталог з docker-compose.production.yml
C="docker compose -f docker-compose.production.yml"

# 1. Які ліміти реально стоять на живих контейнерах.
sudo docker inspect \
  -f '{{.Name}} {{.HostConfig.LogConfig.Type}} {{.HostConfig.LogConfig.Config}}' \
  $($C ps -q)

# 2. Скільки логи важать зараз (з урахуванням ротованих файлів).
for id in $($C ps -q); do
  path=$(sudo docker inspect -f '{{.LogPath}}' "$id")
  printf '%-30s %s\n' \
    "$(sudo docker inspect -f '{{.Name}}' "$id")" \
    "$(sudo du -ch "$path"* 2>/dev/null | tail -1 | cut -f1)"
done
```

Порожній `Config` у першій команді означає, що контейнер створений до появи
`logging:` — його треба перестворити.

### Наслідки, про які варто знати заздалегідь

- **Ротація видаляє, а не архівує.** За межею стелі найстаріший файл зникає.
  `docker compose logs --tail=N` читає лише те, що ще лежить на диску, тому
  вікно вище — це водночас і межа розслідування. Якщо логи мусять жити довше,
  їх треба вивозити з хоста (`journald`, зовнішній збирач) — у compose цього
  свідомо немає, як і вивезення дампів.
- **`LOG_LEVEL` — це і є регулятор обсягу.** `debug` у продакшні збільшує потік
  у кілька разів і відповідно вкорочує вікно в тих самих 50 МБ. Змінна описана в
  [configuration.md](configuration.md).
- **Логи хостового nginx під цю стелю не потрапляють.** Вони належать хостовому
  сервісу, а не Docker, і ротуються `logrotate` із пакета nginx. Якщо
  зворотний проксі підіймали руками, а не з пакета, ротацію треба перевірити
  окремо — це другий за розміром автор записів на цій машині.
- **Стеля не звільняє місце, яке вже зайняте.** Каталог
  `/var/lib/docker/containers/*/` міг набрати гігабайти до цієї зміни; після
  перестворення контейнерів старі файли зникають разом зі старими контейнерами.
  Загальний огляд — `sudo docker system df`.

## Зовнішній моніторинг

Власного сторожа в проєкті немає свідомо: на цьому масштабі зовнішній сервіс
(UptimeRobot, Better Stack, Healthchecks.io) робить те саме, ще й із того боку
мережі — тобто помічає і те, що машина взагалі не відповідає. Але дві речі
потрібно налаштувати саме так, як описано нижче, інакше моніторинг буде
декоративним.

### Чому перевірка порту й «пінг головної» нічого не показують

Хостовий nginx **не є** застосунком. Він слухає 443 і тоді, коли контейнер `api`
мертвий, і тоді, коли Postgres не піднявся: у відповідь піде його власний 502 —
але тільки для шляхів під `/api/`. Усе інше йде в `127.0.0.1:8080`, у nginx
образу `frontend`, а там `try_files $uri $uri/ /index.html` — тобто **будь-який**
невідомий шлях повертає `200` і документ SPA. Перевірка TCP-порту 443 зелена
завжди, поки жива машина.

Гірше: `/health` і `/health/ready` зареєстровані в **корені** Fastify
([`src/app.ts`](../src/app.ts)), а не під префіксом `/api/v1`. Тому наївний
монітор на `https://<домен>/health/ready` без окремого блока в конфізі проксі
потрапляє в те саме `try_files` і отримує `200` з HTML — зелений статус при
повністю мертвому API. Підставити замість цього якийсь маршрут з `/api/v1/`
не можна: там усе за `authenticate`.

Саме для цього в обох шаблонах
[`deploy/nginx/`](../deploy/nginx/) є блок `location = /health/ready` — точний
збіг, який виграє незалежно від порядку правил і не відкриває більше нічого.
`/health` лишається приватним: він відповідає `ok`, поки живий процес, у тому
числі коли Redis лежить, а з непрацюючим Redis лімітер fail-closed і кожен
переклад — 503.

### Що налаштувати

- **HTTP(S)-монітор із перевіркою ключового слова** на
  `https://<домен>/health/ready`, слово — `"redis":"up"`. Саме keyword, а не
  просто код відповіді: код `200` з HTML-документом (див. вище) виглядав би так
  само добре. Тіло віддає лише `up`/`down` по кожній залежності, тому нічого
  чутливого в моніторинг не витікає.
- **Сповіщення в Telegram** у тому самому сервісі. Це і є весь alerting: окремого
  каналу, вебхука чи задачі в застосунку немає й не планується.
- **Вимикач мертвої людини для бекапів** — `BACKUP_HEARTBEAT_URL`, див. нижче.

Інтервал 5 хвилин достатній. Ліміт запитів блоку `/health/ready` (`limit_req
zone=api burst=5`) розрахований саме на монітор, не на опитування щосекунди.

### Бекапи: сповіщення за тишею

Бекап, який перестав робитися, — єдина відмова в цьому стеку, про яку не може
повідомити ніщо інше. `restart: unless-stopped` покриває смерть контейнера, а от
`pg_dump`, що падає щоночі, лише пише в `stderr`; у скрипті свідомо немає
`set -e`, а стеля на логи з часом зітре й ці рядки. Виявляється це в день, коли
знадобилося відновлення.

Тому не проба, а вимикач: `BACKUP_HEARTBEAT_URL` запитується **лише після
повністю успішного дампа** (після `pg_dump`, `gzip`, переносу в `daily/`,
тижневої копії й прибирання старих) — і тривогу підіймає **тиша** з того боку.
Порожнє значення нічого не змінює.

```sh
# у .env, значення видає Healthchecks.io / Better Stack / heartbeat-монітор
BACKUP_HEARTBEAT_URL=https://hc-ping.com/<uuid>
docker compose -f docker-compose.production.yml up -d --force-recreate db-backup
docker compose -f docker-compose.production.yml logs --tail=5 db-backup
```

У лозі має бути `heartbeat enabled, via curl` (або `via wget`) на старті й
`heartbeat sent` після кожного дампа. Період на боці монітора ставте більшим за
добу — наприклад 26 годин: дамп об'єктивно один на добу, і запас потрібен, щоб
рестарт сервера не давав хибної тривоги.

Три властивості, на які варто розраховувати: URL **ніколи** не потрапляє в лог
(хто його має — може тримати монітор спокійним, поки дампів немає, тому й
`stderr` клієнта відкидається); невдалий пінг пише `ERROR` і **не** позначає дамп
невдалим; адреса без схеми зупиняє контейнер при старті з названою помилкою — це
помітно одразу, а не о 03:30. Таймаут 10 с зашитий у скрипті.

## Зворотний проксі: два значення, що відрізняються від типових

У [`deploy/nginx/`](../deploy/nginx/) обидва шаблони хоста задають у `location
/api/` те, що nginx за замовчуванням ставить неправильно **для цього**
застосунку. Обидва промахи виглядали б як помилка застосунку при повністю
здоровому застосунку:

| Директива | Типове | Тут | Чому |
| --------- | ------ | --- | ---- |
| `client_max_body_size` | `1m` | `2m` | `POST /api/v1/transcribe` приймає аудіо в base64, тож ліміт тіла маршруту — `ceil(STT_MAX_AUDIO_BYTES / 3) * 4 + 1024`, тобто ≈1.34 МіБ при типовому 1 МіБ аудіо. З типовим значенням nginx віддав би свій HTML-413 ще до Fastify, і клієнт показав би загальну помилку замість названої `STT_AUDIO_TOO_LARGE`. |
| `proxy_read_timeout` | `60s` | `120s` | Переклад легально буває довгим: кожен провайдер має `AI_TIMEOUT_<ID>` (30 с, 60 с для Ollama) і повторюється `AI_MAX_RETRIES` разів із наростаючою паузою, перш ніж ланцюг перейде до наступного. Типове значення обривало б запит, який ще виконується, віддаючи 504 від nginx. |

Якщо піднімаєте `STT_MAX_AUDIO_BYTES` — підніміть і `client_max_body_size`
(ніколи не нижче за похідний ліміт маршруту). Якщо ланцюг провайдерів довгий,
обмежуйте його `AI_MAX_FALLBACK_ATTEMPTS`, а не подальшим зростанням таймауту:
глобального дедлайну на запит у застосунку немає, тому 120 с покривають
«перший провайдер відмовив поволі, другий відповів», але не будь-який
патологічний ланцюг.

Шаблон `slangua.http.conf.template` — це крок до отримання сертифіката, а не
«полегшена» конфігурація: обидва значення в ньому такі самі, і розходитися
файли не повинні.

## Кеш статики після релізу

nginx усередині образу `frontend`
([`deploy/nginx/frontend.conf`](../deploy/nginx/frontend.conf)) роздає складений
SPA так, як Vite іменує свій вивід: усе під `/assets/` має хеш у назві й
віддається з `immutable` на рік, а `index.html` — з `no-store`. Це і є весь
механізм оновлення: змінений файл має інший URL, а документ, який на ці URL
посилається, не кешується ніколи.

Практичний наслідок: після релізу нічого чистити не треба — але **`index.html`
не має кешуватися і на хостовому nginx**. Закешована копія прив'язує клієнта до
попереднього релізу, а коли старі бандли зникнуть — до білого екрана. Саме так
виглядав старий баг з адмінкою: клієнт виконував код, від якого сервер уже
пішов далі.
