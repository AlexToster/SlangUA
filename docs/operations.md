# Операції

Довідник з експлуатації розгорнутого SlangUA: бекапи, відновлення і ті
налаштування зворотного проксі, які відрізняються від типових не випадково.
Перелік змінних — у [configuration.md](configuration.md), порядок робіт стадії
розгортання — у [`plans/ROADMAP.md`](../plans/ROADMAP.md#stage-9--deployment-in-progress).

## Бекапи Postgres

### Як це працює

Бекапи робить сервіс `db-backup` із
[`docker-compose.production.yml`](../docker-compose.production.yml) — окремий
контейнер на **тому самому образі**, що й база (`postgres:16-alpine`). Це не
дрібниця: `pg_dump` старішої версії відмовляється дампити новіший сервер, тому
при оновленні Postgres обидва теги треба піднімати разом.

Сам розклад — у [`scripts/backup-postgres.sh`](../scripts/backup-postgres.sh),
який змонтований у контейнер лише для читання. Перезбирати образ після правки
скрипта не потрібно, але й `restart` тут не працює:

```sh
docker compose -f docker-compose.production.yml up -d --force-recreate db-backup
```

Монтування **одного файла** прив'язане до inode. Будь-який редактор (і деплой,
який копіює дерево заново) створює новий файл, а контейнер, що вже працює,
продовжує виконувати старий, видалений. `restart` перевикористовує той самий
контейнер разом зі старим монтуванням — тому саме `--force-recreate`.

Що робить скрипт:

- один `pg_dump` на добу о `BACKUP_AT` (UTC), плюс один одразу після старту,
  **якщо** за останні 24 години дампа ще не було. Тому рестарт не пропускає
  добу — і водночас контейнер у циклі падінь не прокручує історію заново;
- пише в тимчасовий файл і переносить його в `daily/` лише коли дамп повністю
  готовий. Недороблений дамп ніколи не потрапляє в каталог і ніколи не
  зараховується як копія;
- `pg_dump` і `gzip` — два окремі кроки, а не конвеєр: POSIX-оболонка не бачить
  код виходу лівої частини `|`, тож зламаний дамп у конвеєрі виглядав би
  успішним;
- у неділю (ISO-день 7) додатково створює **жорстке посилання** на той самий
  файл у `weekly/`. Тижнева копія не займає місця, поки живі обидва імені, а
  видалення одного не чіпає інший;
- тримає `BACKUP_KEEP_DAILY` найновіших файлів у `daily/` і
  `BACKUP_KEEP_WEEKLY` у `weekly/`, рахуючи лише `*.sql.gz` — сторонні файли в
  каталозі не зникають;
- падіння одного дампа не завершує розклад: у скрипті свідомо немає `set -e`.
  Помилка йде в `stderr` контейнера, наступна спроба буде за розкладом.

Формат — звичайний SQL, стиснений gzip: для відновлення потрібен лише `psql`.
Процедура, яку виконують під тиском, не повинна залежати ні від чого більшого.

Ім'я файлу — час дампа за UTC: `slangua-20260827T033000Z.sql.gz`.

### Перевірити, що бекапи справді робляться

Розклад — не доказ. Команди нижче припускають типовий `BACKUP_DIR=./backups` —
підставте свій шлях у `B`, бо оболонка хоста змінних із `.env` не бачить.

```sh
cd /opt/slangua                       # каталог з docker-compose.production.yml
C="docker compose -f docker-compose.production.yml"
B=./backups

# 1. Позачерговий дамп прямо зараз (те саме, що робити перед міграцією).
$C run --rm --entrypoint sh db-backup /usr/local/bin/backup-postgres.sh --once

# 2. Що лежить у каталозі і якого розміру.
sudo ls -lh "$B"/daily "$B"/weekly

# 3. Лог сервісу: рядок `wrote daily/...` на кожен дамп, `ERROR` на кожну невдачу.
$C logs --tail=50 db-backup
```

Дамп нульового або підозріло малого розміру — це не бекап. Цілісність архіву
перевіряється без розпакування:

```sh
sudo gzip -t "$B"/daily/slangua-<стамп>.sql.gz && echo ok
sudo zcat "$B"/daily/slangua-<стамп>.sql.gz | head -20
```

У другій команді має бути шапка `pg_dump` і `CREATE TABLE`, а не порожньо.

### Відновлення з дампа

Це руйнівна операція: вона знищує поточний вміст бази. Перед нею варто зробити
`--once` — навіть якщо база здається зламаною, її поточний стан ще може
знадобитися.

```sh
cd /opt/slangua                       # каталог з docker-compose.production.yml
C="docker compose -f docker-compose.production.yml"
B=./backups                           # ваш BACKUP_DIR

# 1. Прибрати тих, хто пише в базу. Frontend хай лишається — користувач побачить
#    помилку застосунку, а не порожню сторінку.
$C stop api db-backup

# 2. Чиста база. Дамп знятий із --no-owner --no-privileges, тому відновлюється
#    під того користувача, яким запущений psql.
$C exec -T db psql -U slangua -d postgres -c 'DROP DATABASE slangua;'
$C exec -T db psql -U slangua -d postgres -c 'CREATE DATABASE slangua OWNER slangua;'

# 3. Залити дамп. Файли належать root, тому gunzip іде через sudo, а psql --
#    через socket у контейнері, де пароль не потрібен.
sudo gunzip -c "$B"/daily/slangua-<стамп>.sql.gz \
  | $C exec -T db psql -U slangua -d slangua -v ON_ERROR_STOP=1

# 4. Підняти застосунок. `prisma migrate deploy` у команді сервісу застосує ті
#    міграції, яких у дампі ще не було, -- це штатний випадок, якщо образ новіший
#    за дамп.
$C start api db-backup

# 5. Переконатися, що піднялося і дані на місці.
curl -fsS http://127.0.0.1:3000/health/ready && echo
$C exec -T db psql -U slangua -d slangua \
  -c 'SELECT count(*) AS users FROM "User";' \
  -c 'SELECT count(*) AS translations FROM "Translation";'
```

`ON_ERROR_STOP=1` тут обов'язковий: без нього `psql` дійде до кінця файлу,
проковтнувши помилки, і залишить напівживу базу з нульовим кодом виходу.

Після відновлення всі активні сесії стають недійсними: `RefreshToken` — рядки в
базі, і ті, що були видані після зняття дампа, у ній відсутні. Користувачі
переавтентифікуються самі при наступному відкритті Mini App; окремих дій це не
потребує.

### Чого бекапи не покривають

- **Redis не дампиться, і це рішення, а не пропуск.** Там немає нічого, що не
  відтворюється саме: ліміти згасають за вікном, кеш preview зашифрований і
  короткоживучий, метрики адмінки згасають за термінами ключів. Єдине, що
  переживає рестарт, — кіл-світч провайдерів (`ai:provider:disabled`), і його
  дешевше поставити руками, ніж відновлювати з копії. `appendonly yes` у сервісі
  `redis` тримає дані між перезапусками контейнера; втрата томика Redis коштує
  скинутих лімітів, а не даних користувачів.
- **Шифрування дампів немає.** Дамп — це повний текст усіх перекладів і
  Telegram-id усіх користувачів. Тому контейнер працює від `root` і не
  поступається правами, а скрипт додатково ставить `umask 077`: каталоги
  `daily/` і `weekly/` виходять `0700`, файли — `0600`. Самого лише `root` як
  власника було б **недостатньо** — типовий `umask 022` дав би `0644`, тобто дамп
  читав би будь-який акаунт на хості. Якщо каталог існував до появи `umask`,
  права виправляються один раз: `sudo chmod -R go-rwx "$BACKUP_DIR"`. `BACKUP_DIR`
  також не має лежати там, куди дивиться вебсервер. Якщо дампи виїжджають із
  машини — шифруйте їх на тому боці.
- **Копія на тому ж диску — не бекап від втрати диска.** `BACKUP_DIR` захищає від
  помилкового `DELETE`, невдалої міграції і зіпсованого тому Postgres, але не від
  смерті машини. Вивезення копії на інший хост — окрема задача оператора
  (`rsync`/`scp` за розкладом на хості), у compose її свідомо немає: інакше
  репозиторій мусив би знати адресу й ключ чужого сервера.
- **`.env` у дамп не входить.** Без `PREVIEW_ROOT_KEY`, `JWT_SECRET` і
  `REFRESH_TOKEN_HMAC_SECRET` відновлена база працює, але всі сесії й preview-кеш
  недійсні. Копія `.env` зберігається окремо від репозиторію й окремо від дампів.

### Що перевірено, а що ні

Скрипт перевірений у Linux-пісочниці із заглушками замість `pg_dump`/`pg_isready`:
синтаксис (`sh -n`, `dash -n`), режим `--once`, жорстке посилання тижневої копії
(той самий inode), права після `umask 077` (каталоги `0700`, дампи `0600`),
утримання 7/4 із видаленням найстаріших і без дотику до
сторонніх файлів, невдача `pg_dump` (файл не лишається, код виходу 1),
пропуск дампа на старті, коли свіжий уже є, арифметика розкладу для «октальних»
годин (`08:30`, `09:09`) і зупинка на некоректних `BACKUP_AT`/`BACKUP_KEEP_*`.

**Справжнє відновлення на розгорнутому сервері ще не виконувалося.** Процедура
вище написана, але не відрепетирувана — це пункт
[9.9](../plans/ROADMAP.md#stage-9--deployment-in-progress) («відновлення, яке
виконали»). До того моменту бекапи слід вважати перевіреними лише як механіка
зняття копій.

## Зворотний проксі: два значення, що відрізняються від типових

У [`deploy/nginx/`](../deploy/nginx/) обидва шаблони хоста задають у `location
/api/` те, що nginx за замовчуванням ставить неправильно **для цього**
застосунку. Обидва промахи виглядали б як помилка застосунку при повністю
здоровому застосунку:

| Директива | Типове | Тут | Чому |
| --------- | ------ | --- | ---- |
| `client_max_body_size` | `1m` | `2m` | `POST /api/v1/transcribe` приймає аудіо в base64, тож ліміт тіла маршруту — `ceil(STT_MAX_AUDIO_BYTES / 3) * 4 + 1024`, тобто ≈1.34 МіБ при типовому 1 МіБ аудіо. З типовим значенням nginx віддав би свій HTML-413 ще до Fastify, і клієнт показав би загальну помилку замість названої `STT_AUDIO_TOO_LARGE`. |
| `proxy_read_timeout` | `60s` | `120s` | Переклад легально буває довгим: кожен провайдер має `AI_TIMEOUT_<ID>` (30 с, 60 с для Ollama) і повторюється `AI_MAX_RETRIES` разів із наростаючою паузою, перш ніж ланцюг перейде до наступного. Типове значення обривало б запит, який ще виконується, віддаючи 504 від nginx. |

Якщо піднімаєте `STT_MAX_AUDIO_BYTES` — підніміть і `client_max_body_size`
(ніколи не нижче за похідний ліміт маршруту). Якщо ланцюг провайдерів довгий,
обмежуйте його `AI_MAX_FALLBACK_ATTEMPTS`, а не подальшим зростанням таймауту:
глобального дедлайну на запит у застосунку немає, тому 120 с покривають
«перший провайдер відмовив поволі, другий відповів», але не будь-який
патологічний ланцюг.

Шаблон `slangua.http.conf.template` — це крок до отримання сертифіката, а не
«полегшена» конфігурація: обидва значення в ньому такі самі, і розходитися
файли не повинні.

## Кеш статики після релізу

nginx усередині образу `frontend`
([`deploy/nginx/frontend.conf`](../deploy/nginx/frontend.conf)) роздає складений
SPA так, як Vite іменує свій вивід: усе під `/assets/` має хеш у назві й
віддається з `immutable` на рік, а `index.html` — з `no-store`. Це і є весь
механізм оновлення: змінений файл має інший URL, а документ, який на ці URL
посилається, не кешується ніколи.

Практичний наслідок: після релізу нічого чистити не треба — але **`index.html`
не має кешуватися і на хостовому nginx**. Закешована копія прив'язує клієнта до
попереднього релізу, а коли старі бандли зникнуть — до білого екрана. Саме так
виглядав старий баг з адмінкою: клієнт виконував код, від якого сервер уже
пішов далі.
