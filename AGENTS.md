# SlangUA — Agent Working Agreement

## Quality with a small context budget

- Починай із короткого результату й наступної дії; не переказуй код, diff або документацію, якщо користувач цього не просить.
- Перед дією визначай найменший достатній scope: конкретний маршрут/сервіс/компонент і його прямі тести. Спочатку використовуй `rg`, потім читай лише знайдені файли або потрібні розділи.
- Не скануй увесь репозиторій, не перечитуй уже перевірені файли та не запускай повний набір тестів для косметичних чи документаційних змін.
- Один раз на початку зміни перевіряй `git status`; вважаєш наявні незв'язані зміни користувацькими й не змінюєш їх.
- Об'єднуй незалежні read-only перевірки в один виклик. Перед повторним пошуком використовуй уже зібрані факти, якщо файли не змінювалися.

## Джерела правди

- API та DTO: `plans/docs/04-api.md` і поточні `src/routes/**` / `src/services/**`.
- Security, Redis, auth і rate limits: `plans/docs/06-security.md` та код плагінів/сервісів.
- Style Engine: `plans/docs/07-styles.md` і `src/style-engine/**`.
- Telegram Mini App UX: `plans/docs/08-frontend-design.md`; inline sharing: `plans/docs/09-telegram-sharing.md`.
- Якщо документація та код розходяться, повідом розбіжність, визнач джерело правди для поточного завдання й онови обидва лише коли зміна входить у запит.

## Зміни

- Робити маленькі, цілісні patch-и; за можливості тримати refactor, cleanup і функціональну зміну окремими для легшого review.
- Проактивно виявляти й пропонувати доречні refactor-и, cleanup та додаткові покращення; чітко відділяти їх від основного запиту.
- Не вигадувати API, не послаблювати age gate, auth, ownership, rate limits, prompt-injection checks або server-side validation заради UI.
- Для preview/save/share не довіряти тексту чи ідентифікаторам від клієнта: перевіряти користувача, TTL, ownership та ідемпотентність на сервері.
- При зміні контракту синхронно оновлювати маршрут, сервіс, інтеграційний тест і `04-api.md`; для security/UX змін також оновлювати відповідний документ вище.

## Перевірка пропорційно до ризику

- Backend TypeScript: спочатку `npm run test:typecheck`; route/service/Prisma/Redis зміни — релевантний integration test, потім `npm test` перед handoff.
- Frontend: після UI/стану запускати найвужчий релевантний test; перед handoff — `npm run lint`, `npm run test -- --run` і `npm run build` у `frontend/`.
- Документація: перевірити посилання, назви маршрутів і `git diff --check`; не запускати build без потреби.
- Невдалий тест — спочатку ізолюй причину; не маскуй його зміною очікування чи вимкненням тесту без доказів, що контракт змінився навмисно.

## Комунікація

- Для багатокрокових або ризикових задач коротко називай припущення, scope і критерій готовності. Для простих задач — діюй без зайвого плану.
- Якщо залишку контексту може не вистачити для якісного завершення задачі, до початку великої зміни повідом ризик і запропонуй розбити роботу на логічні етапи з окремими критеріями готовності.
- Повідомляй лише нові суттєві факти, blockers, файли, що змінилися, і фактично виконані перевірки. Не заявляй, що щось протестовано, якщо команда не запускалася.
